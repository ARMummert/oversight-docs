RFC-003 - Streaming Analytics & Anomaly Detection

Author: Amy Mummert

Status: Proposed

Date: 2026-21-26

Target Components: Stateful Streaming Analytics Service, NATS JetStream Telemetry Consumers, Redis Hot Cache, TimescaleDB Analytics Persistence

Background / Context

Oversight ICS requires streaming analytics and anomaly detection that is able to ingest a large volume of data and process it continuously. To do this, Oversight proposes the implementation of a streaming engine that detects statistical drift and abnormal operating behavior.

The streaming analytics service consumes the normalized telemetry events from NATS JetStream and performs real-time statistical analysis on the data before reaching the cognitive reasoning layer. The streaming analytics service provides a boundary between telemetry transport and cognitive reasoning and maintains the following:

  • Rolling analytical state
  • Calculates statistical metrics
  • Identifies statistical drift
  • Applies persistence and hysteresis rules
  • Publishes anomaly events for authorized downstream consumers

The streaming analytics service does NOT:

  • Determine root cause analysis
  • Perform RAG operations
  • Generate control intents
  • Authorize commands
  • Select failover actions
  • Execute commands against field assets
  • Modify PLC control logic
  • Modify SIS Logic

By implementing the streaming analytics service, Oversight will be able to provide a real-time, continuous, and persistent view of the telemetry data without possessing control authority.

Problem Statement

Industrial telemetry data contains normal process variables, measurement noise, startup and shutdown transients, network jitter, sensor drift, and approved changes in the operating state.

If Oversight were to send every telemetry value directly to the cognitive reasoning layer, it would create several problems:

  1. An increased sensitivity to normal process noise and measurement noise
  2. Increased false-positives
  3. Increased processing load on downstream reasoning services
  4. Alarm chatter caused by transient threshold crossings
  5. Loss of statistical context between individual measurements
  6. Difficulty distinguishing between sustained process drift and transient excursions
  7. Difficulty detecting gradual degradation that may remain within operating limits
  8. Reduced ability to reproduce and explain exactly what happened
  9. Increased risk of downstream reasoning services operating on stale, uncertain, or invalid telemetry

Oversight therefore requires a streaming analytics service that is capable of maintaining state across telemetry events and evaluating measurements against their recent operational history.

The streaming analytics service must perform the following:

  1. Stateful stream processing
  2. Per-signal analytical state
  3. Rolling statistical windows
  4. Rolling mean calculations
  5. Rolling standard deviation calculations
  6. Windowed $Z$-score calculations
  7. Configurable anomaly thresholds
  8. Hysteresis for anomaly state transitions
  9. Persistence requirements for analytical state and anomaly events
  10. Telemetry quality checks and validation of incoming telemetry
  11. Detection of stale or missing telemetry
  12. Cold-start and window warm-up behavior
  13. Replayable and reproducible anomaly detection
  14. Low-latency processing of high-frequency telemetry
  15. Idempotent handling of redelivered telemetry events
  16. Publication of deterministic anomaly events
  17. Monitoring of consumer lag, processing latency, and analytical health

The streaming analytics service must remain non-authoritative for control operations. It is for detecting anomalies that Oversight will then use to inform the cognitive reasoning layer.

!!! “Anomaly Detection” Detection of an anomaly must not directly result in physical actuation.

Proposed Solution

The proposed solution is to implement a stateful streaming analytics service that consumes telemetry events from NATS JetStream and processes them in real-time. The streaming analytics service will perform statistical analysis on the telemetry data.

Initial Implementation

  • Python – for the analytics service
  • NATS JetStream durable pull consumers: for telemetry ingestion
  • Protocol Buffers: for telemetry and event serialization
  • Redis: for current hot analytical state and anomaly events
  • TimescaleDB: for analytical history and recovery

This implementation may be replaced by another stateful stream-processing framework (e.g., Apache Flink) in the future without changing the telemetry or anomaly event contracts.

Goals

  1. Stateful streaming analytics service
  2. Rolling statistical windows
  3. Rolling mean calculations
  4. Rolling standard deviation calculations
  5. Windowed $Z$-score calculations
  6. Configurable anomaly thresholds
  7. Hysteresis for anomaly state transitions
  8. Persistence requirements for analytical state and anomaly events

Architectural Design Principles

Deterministic Statistical Processing

The Oversight streaming analytics service must process telemetry data deterministically. This means that the same telemetry data must always produce the same statistical results. This model does not rely on LLM, RAG lookup, or other non-deterministic reasoning. It provides data consistency, auditability, and precision.

Separation of Detection & Decision-Making

The streaming analytics service identifies statistical anomalies. It does not make any decisions or take any actions.

If an anomaly is detected, the event is published to the oversight.events.> subject, but that event does not contain authorization to take any control action.

The streaming analytics service must not publish to oversight.commands.>.

Source-Protocol Independence

The streaming analytics service only uses the telemetry contracts defined by Oversight. It does not depend on any specific protocol.

It must not require any of the following:

  • Modbus register addresses
  • OPC UA NodeIDs
  • EtherNet/IP or CIP addresses
  • MQTT topic structures
  • Sparkplug B source names
  • vendor-specific device addressing

All source-specific information must be terminated by the Northbound Ingest Service before reaching the streaming analytics service.

At-least-once Delivery Awareness

NATS Jetstream may redeliver telemetry based on the acknowledgement and recovery behavior of the system. The streaming analytics service has to be able to handle those redeliveries. However, the redelivered telemetry must not be counted as a new statistical sample. The TelemetryEvent contract contains a unique message_id field that can be used to identify telemetry that has been redelivered.

Stateful Isolation (State-Key Resolution)

Each monitored telemetry signal maintains an independent state. Every telemetry event is resolved to a state key that will uniquely identify the telemetry signal whose state is being updated.

State Key:

Enterprise.Site.Area.Line.Asset.Tag

All telemetry events with the same signal resolve to the same state key where rolling windows, statistical baselines, persistence counters, hysteresis state, and anomaly state that are associated with one key must remain isolated from the state belonging to another key.

Example:

Pump_01.Discharge_Pressure remains independent of Pump_01.Motor_Current even though they both belong to the same asset.

Data Quality Before Analytics

A telemetry event must be validated and pass quality checks before it can perform statistical analysis. Malformed, invalid, stale, or ineligible telemetry must not silently enter an analytical window.

Fail-Safe Analytics

A failure of the streaming analytics service must not result in the loss of telemetry data or cause raw telemetry to be interpreted as valid statistical output.

The service must be placed in a DEGRADED state if any of the following conditions are met:

  1. Loss of analytical state
  2. Invalid calculations
  3. Analytics service failure

Replayable Anomaly Detection

Oversight must be able to replay anomalies that have been detected and published to the cognitive reasoning layer. This is necessary for auditing, reproducibility, and explainability of the anomaly detection process.

Historical replays of anomalies must be distinguished from live real-time processing and replayed data must not be allowed to present itself as a new live anomaly.

Streaming Analytics & Data Flow

Telemetry Ingestion

  1. The streaming analytics service subscribes to the oversight.telemetry.> subject
  2. The system uses a durable JetStream pull consumer to receive telemetry events from NATS JetStream
  3. Pull-based consumption allows Oversight to control the following:
  4. Batch size
  5. Processing rate
  6. Acknowledgement timing
  7. Backpressure
  8. Retry Behavior
  9. Consumer concurrency
  10. The service must acknowledge a message only after the message has been successfully processed and persisted to the analytical state and history. This ensures that the service can recover from failures without losing telemetry data.

Telemetry Quality Evaluation

Incoming telemetry observation must have its quality validated before it can be processed.

Quality State

  1. GOOD - telemetry is valid and can be processed
  2. BAD - telemetry is invalid and must not be processed
  3. UNCERTAIN - telemetry is questionable and must not be processed

Telemetry Validation

Before any statistical processing takes place, the streaming analytics service must validate the telemetry event. The following validation steps are required:

  1. schema_version (e.g., 1.0.0, telemetry.v1)
  2. message_id (e.g., UUIDv4)
  3. semantic_identity (e.g. Enterprise.Site.Area.Line.Asset.Tag)
  4. value (e.g., 72.4)
  5. timestamp (e.g., 2024-06-01T12:34:56.789Z)
  6. data_type (e.g., FLOAT64, INT32, BOOLEAN)
  7. quality (e.g., GOOD, BAD, UNCERTAIN)
  8. Any Required Metadata (e.g., engineering_unit="psi", sample_interval_ms=100, analytics_profile="pump_pressure_v1")
  9. Distributed tracing metadata (e.g., trace_id, correlation_id)

If a schema validation error occurs, the service must not let the message enter the statistical baseline.

Duplicate Detection

Oversight uses the abilities of NATs JetStream to detect duplicate telemetry events. Because NATS JetStream provides at-least-once delivery, redelivery is possible inside the streaming analytics service.

To prevent duplicates, the analytics service must not use the same message_id for two telemetry events and any redelivered attempt must not be treated as a new statistical sample.

State-Key Resolution

Each telemetry event is given an analytical state key that identifies which analytical window receives the measurement.

Example: AcmeCorp.Longview_Plant.WaterTreatment.Filtration.Pump_01.Discharge_Pressure

Timestamp & Freshness Validation

The streaming analytics service must be able to distinguish the different information each timestamp provides. The following timestamps are used:

  1. source_timestamp - the timestamp of the source device (physical observation)
  2. ingest_timestamp - the timestamp when the NIS received the telemetry event from the source device
  3. analytics_timestamp - the timestamp when the telemetry event was processed by the streaming analytics service

Both source_timestamp and ingest_timestamp can be used to determine several analytical metrics:

  1. ingest_latency_ms - arrival -> ingestion
  2. source_latency_ms - observation -> ingestion
  3. freshness_ratio - the ratio of ingest_latency_ms to source_latency_ms
  4. freshness_threshold_ms - the configured freshness threshold
  5. freshness_threshold_ratio - the ratio of ingest_latency_ms to freshness_threshold_ms
  6. processing_latency_ms - ingestion -> processing
  7. processing_latency_ratio - the ratio of ingest_latency_ms to processing_latency_ms
  8. consumer_lag_ms - last processed telemetry event -> last received telemetry event
  9. consumer_lag_ratio - the ratio of consumer_lag_ms to ingest_latency_ms

Any telemetry event older than the configured freshness threshold must not be processed.

Out-of-Order Telemetry

There are several reasons why telemetry events may arrive out-of-order. These include, network jitter, polling delays, source buffering, reconnection, NATS redelivery, and consumer backpressure.

Breakdown:

  • The statistical analytics service records the timestamps of the last accepted live observation.
  • If that observation is older than the configured freshness threshold, it must not alter the statistical state.
