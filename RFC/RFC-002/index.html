RFC-002 - Northbound Ingest Service & Protocol Normalization

Author: Amy Mummert

Status: Proposed

Date: 2026-09-01

Target Components: Northbound Ingest Service, Protocol Adapters, Protocol Normalization, Telemetry Mapping

Background / Context

This RFC defines the proposed design and operation of the Northbound Ingest Service (NIS) and the protocol normalization pipeline.

The Oversight system relies on strict separation between OT and IT environments. Telemetry must move northbound from the field assets and control assets into the Level 3.5 demilitarized zone without allowing downstream consumers to establish direct connections to those assets.

Field assets, PLCs, RTUs, gateways, and supervisory systems may expose telemetry through a variety of protocols (e.g., Modbus, OPC UA, Ethernet/IP, MQTT/Sparkplug B). Each source protocol processes information differently:

  • Modbus TCP:
  • Process data - coils, discrete inputs, input registers, and holding registers
  • Accessed using function codes and addresses.
  • OPC UA:
  • Typed process values – Uses NodeIds.
  • A returned value may contain a value, source timestamps, server timestamps, and status codes.
  • Ethernet/IP:
  • Implements the CIP (Common Industrial Protocol) using objects, instances, attributes, assemblies, and explicit or implicit messaging
  • MQTT / Sparkplug B:
  • Industrial process metrics using the Sparkplug B MQTT topic namespace, payload model, and state management (such as birth and death notifications)

These protocols are not suitable for the internal telemetry contract for Oversight. Allowing downstream consumers to have direct access to these protocols would tightly couple Oversight to the individual industrial protocols. This would expose raw protocol-specific information to downstream consumers. This presents a security risk and increases the complexity of the system.

Problem Statement

Oversight ICS is designed to ingest high-throughput telemetry exceeding 10,000 points per second from the deterministic control layers. The Northbound Ingest Service must communicate with industrial protocols, however, to remain secure, protocol-specific information must be terminated at the ingestion boundary and must not be exposed directly to downstream consumers.

If we were to allow downstream consumers (Bytewax, TimescaleDB, Redis, LangGraph Agent) to consume the protocol-specific data directly, this would tightly couple Oversight to individual industrial protocols.

Without protocol normalization, every downstream consumer would need to understand those raw industrial protocols, which increases the attack surface and is a huge safety risk. This would also reduce hardware abstraction and increase the complexity of the system.

In addition, unmanaged polling, subscription, or connection behavior against field controllers can introduce an excessive load on the system.

Proposed Solution

The proposed solution is to implement the Northbound Ingest Service (NIS) as a read-only service that ingests telemetry and normalizes it into the Oversight TelemetryEvent contract.

The NIS will contain dedicated protocol adapters for the following industrial protocols:

  • Modbus TCP
  • OPC UA
  • Ethernet/IP
  • MQTT / Sparkplug B

Each adapter will establish controlled, read-only communication with approved field endpoints. The adapter does the following:

  • Terminates the source-protocol
  • Decodes the received data
  • Converts the data into an internal raw-observation representation

Protocol-specific identifiers (e.g., modbus register addresses, OPC UA NodeIds, Ethernet/IP CIP object paths, and Sparkplug B MQTT topics) will remain within the protocol adapters and telemetry mapping layers.

The internal raw-observation will then be passed to the NIS normalization layer. The normalization layer will use a telemetry mapping registry and will perform the following:

  • Determines the enterprise, site, area, line, asset, and tag identity
  • Converts the source value into the required data-type
  • Applies byte-order conversion where it is required
  • Applies configured scaling factors and offsets
  • Normalizes engineering units
  • Normalizes the source quality information into the Oversight quality model
  • Normalizes the source timestamp and assigns an ingestion timestamp
  • Detects malformed, stale, unsupported, or unmapped telemetry

The normalized telemetry will then be used to construct the TelemetryEvent. The NIS will validate the event with the supported schema before allowing it to be published to the UNS.

Using protocol buffers, the NIS will serialize the TelemetryEvent. It then constructs the NATS subject using the following format:

oversight.telemetry.<enterprise>.<site>.<area>.<line>.<asset>.<tag>

The NIS will then publish the Protobuf-serialized TelemetryEvent to the UNS subject. The NIS will confirm success only after receiving a JetStream PubAck acknowledgement.

Component Responsibilities

The NIS provides a controlled boundary between source protocol communication and the internal telemetry contract.

The Responsibilities of Northbound Ingest Service are as follows:

  • The NIS ingests telemetry through read-only connections to approved industrial telemetry sources.
  • It terminates source-protocol communication at the Northbound Ingest Service boundary. This is important because protocol-specific information must never be exposed to downstream consumers.
  • It reads and decodes the following industrial protocols:
  • Modbus TCP
  • OPC UA
  • Ethernet/IP
  • MQTT / Sparkplug B
  • It reads protocol-specific data, translates it into vendor-neutral Oversight ICS telemetry.
  • The NIS NEVER: Writes to the control assets, processes command subjects, detects anomalies, or performs any physical control.
  • The NIS normalizes data types, byte order, scaling, offsets, engineering units, quality, and timestamps.
  • Constructs and validates the Oversight TelemetryEvent.
  • Serializes the TelemetryEvent objects using Protocol Buffers.
  • Builds the semantic UNS subject from the TelemetryEvent.
  • Publishes the protobuf-serialized TelemetryEvent to the UNS subject oversight.telemetry.>.
  • Confirms the successful JetStream persistence through a publish acknowledgement (PubAck).

MQTT / Sparkplug B messages are decoded at the NIS boundary and mapped into the Oversight telemetry contract, rather than being forwarded directly to the UNS.

The NIS is Read-Only and does not replace PLC control logic, safety-instrumented systems, or deterministic control functions. It has no authority to write to field assets or execute control commands.

Goals

  1. Safely collect OT Telemetry
  2. Communicate only with approved field endpoints.
  3. Use read-only requests and subscriptions.
  4. Prevent downstream consumers from having direct connections to field assets.
  5. Hardware & Protocol Abstraction
  6. Terminate source-protocol communication at the NIS boundary.
  7. Prevent physical addresses, NodeIds, CIP object paths, Sparkplug B topics, and vendor-specific identifiers from being exposed to downstream consumers.
  8. Allow downstream components to use the telemetry contract without knowing the original protocol.
  9. Keep the telemetry identity stable if a device, address, or source protocol changes.
  10. Telemetry
  11. Map each source value to the correct enterprise, site, area, line, asset, and tag identity.
  12. Normalize data types, byte order, scaling, offsets, engineering units, quality, and timestamps.
  13. Build and validate the Oversight TelemetryEvent.
  14. Serialize the TelemetryEvent objects using Protocol Buffers.
  15. Publish Telemetry to the UNS
  16. Build the UNS subject oversight.telemetry.>.
  17. Publish the protobuf-serialized TelemetryEvent to NATS JetStream.
  18. Confirm JetStream accepted the message through a publish acknowledgement (PubAck).
  19. Provide Reliable & Measurable Operations
  20. Measure telemetry throughput and latency.
  21. When connection fails: Use limited retries and controlled backoff.
  22. Detect and report stale, invalid, unsupported, unmapped, rejected, or dropped telemetry.
  23. Do not let telemetry fail or disappear without being detected and reported.
  24. Test the NIS for performance, reliability, and read-only requirements.

Non-Goals

The NIS is not responsible for:

  1. Writing to field devices
  2. Processing commands
  3. Controlling PLC or Safety Logic
  4. Long-term audit and historian retention
  5. Command validation, authorization, signing, or execution
  6. Bytewax analytics and anomaly detection
  7. SIS Control Logic
  8. Redis & TimescaleDB schemas
  9. NATS stream retention and replication configuration

Internal Modules

Protocol Adapters

Protocol adapters communicate with approved telemetry sources.

  • The Oversight NIS includes adapters for: Modbus TCP, OPC UA, Ethernet/IP, and MQTT/Sparkplug B.
  • Each adapter does the following:
  • Opens and manages a read-only connection or subscription
  • Reads or receives telemetry
  • Decodes the source protocol message
  • Prevents protocol-specific information from leaving the adapter boundary
  • Passes the decoded data to the raw-observation interface

Raw-Observation Interface

The raw-observation interface is the interface between the protocol adapters and the normalization layer. It is a temporary internal representation of the telemetry data.

  • The raw-observation interface contains:
  • A mapping identifier (e.g., modbus register address, OPC UA NodeId, CIP object path, Sparkplug B topic)
  • The raw value (e.g., integer, float, string, boolean, array)
  • The source timestamp
  • The source quality information (e.g., status, flags, error codes)
  • The time the NIS received the observation

This raw-observation is only used inside the NIS and is not published to the UNS.

Telemetry Mapping Registry

The mapping registry contains the telemetry mapping rules. It is used to map the raw-observation interface to the Oversight TelemetryEvent contract (e.g., enterprise, site, area, line, asset, tag).

The mapping registry contains: - Data Type - Byte Order - Scaling Factor - Offset - Engineering Units - Expected update interval - Stale-data threshold - Mapping version

Physical addresses and protocol identifiers remain in the mapping registry and are not included in the published telemetry.

Normalization Layer

The normalization layer converts the raw-observation into vendor-neutral Oversight ICS telemetry.

It performs the following:

  • Converts the data type
  • Corrects byte order
  • Applies scaling and offsets
  • Converts engineering units
  • Normalizes quality
  • Normalizes timestamps
  • Detects stale, malformed, unsupported, or unmapped telemetry

Schema Validator

The schema validator checks the completed TelemetryEvent against the Oversight TelemetryEvent schema.

It verifies the following:

  • All required fields are present
  • The semantic identity is valid
  • Exactly one telemetry value is set
  • The quality value is supported
  • Timestamps are valid
  • The schema version is supported
  • The payload does not contain prohibited protocol-specific information

Protobuf Serializer

The Protobuf serializer converts a valid TelemetryEvent into binary Protocol Buffer bytes.

Durable Store-and-Forward Spool

  • Persists events before publication
  • Tracks pending and acknowledged records
  • Replays records after recovery
  • Does not delete or overwrite unacknowledged spool records
  • When the spool is at capacity, it will change its readiness to NOT_READY and will not publish telemetry until the spool is drained below the configured threshold.
  • Disk full, read-only file system, checksum failures, and spool corruption must be specified failure modes.
  • Telemetry gaps are recorded when the spool is unavailable.

Replicated Spool

The durable store-and-forward spool protects accepted telemetry against an NIS process failure, active-host failure, and failover to the standby NIS instance.

To achieve this, Oversight uses a replicated spool design. Each NIS will maintain a persistent disk-backed spool on a separate host and failure domain.

Endpoint Ownership

  • Only one NIS instance is allowed to actively poll or subscribe to an endpoint at a time.
  • The NIS instance must acquire ownership before connecting to the endpoint.

Each endpoint must have:

  • One active owner
  • An optional standby owner
  • A way to determine the current ownership generation
  • A timeout for detecting ownership before connecting to the endpoint.

NATS Publisher

The NATS publisher does the following:

  • Builds the oversight.telemetry.> subject
  • Publishes the Protobuf payload to NATS JetStream
  • Waits for JetStream to publish an acknowledgement (PubAck)
  • Uses bounded retries when publication fails
  • Reports unsuccessful, spooled, unacknowledged, or failed publications

Health & Diagnostics

The health and diagnostics of the NIS report the following:

  • Adapter connection state
  • Last successful observation
  • Points received, normalized, published, and rejected
  • Unmapped or stale points
  • Normalization and validation failures
  • Retry counts
  • Publication failures
  • Processing and publication latency

The following payload defines the information that every downstream consumer receives:

Typed Values

A TelemetryEvent represents one normalized telemetry point. Each event contains one data_type and one value, to avoid ambiguous values (e.g., “value”: “72.4” could be text, integer, double, or binary). The TelemetryEvent must contain these fields so that downstream consumers can process it correctly.

The value field uses google.protobuf.Value. This allows Protobuf to preserve the existing JSON payload.

{
  "data_type": "DOUBLE",
  "value": 72.4
}

The NIS must reject telemetry events that are missing a data_type or if the data_type is set to DATA_TYPE_UNSPECIFIED. Events that are missing a value or are null are also rejected.

The following are also cause for rejection:

  • value does not match data_type
  • Integer is a fractional value
  • Unsigned Integer is a negative value
  • A numeric value exceeds its allowed range
  • A double contains NaN, positive infinity, or negative infinity
  • A binary value is not a valid base64

Quality Values

Quality values are used to indicate the reliability of the telemetry value.

  • GOOD
  • BAD
  • UNCERTAIN
  • UNKNOWN

A TelemetryEvent with a BAD quality may still be published to downstream consumers so that they know that the current measurement is not reliable.

Timestamp Rules

  1. ingested_at - required and assigned by the NIS.
  2. source_timestamp - included only when the source provides a timestamp.
  3. The NIS will not create a fake source timestamp when one is unavailable.
  4. All timestamps must use UTC.
  5. Protobuf timestamps use google.protobuf.Timestamp format.
  6. Replayed telemetry must set is_replay to true.
  7. Live telemetry must set is_replay to false.

Engineering Unit Policy

Engineering units are assigned by the telemetry mapping registry. The NIS must use an approved list of engineering unit codes so that the same unit is always written the same way (e.g., PSI for pounds per square inch are all normalized to “psi”).

For the NIS, UCUM (Unified Code for Units of Measure) is used to define engineering units. UCUM codes should be used for numeric measurements. Numeric values without a physical unit of measurement are to use the UCUM code 1. Boolean and string values do not require an engineering unit.

UCUM

Schema Validation Rules

Before publishing a TelemetryEvent to the UNS, the NIS must validate the following:

  1. schema_version is supported
  2. message_id is a valid UUIDv4
  3. All identity fields are present
  4. payload.value matches payload.data_type
  5. The identity matches the NATS subject
  6. ingested_at is present and valid
  7. source_timestamp is valid when present
  8. engineering_unit follows the approved unit policy
  9. When quality is BAD or UNCERTAIN, the quality_reason must be set to the appropriate quality_reason value.
  10. The event does not contain prohibited protocol-specific information or physical addresses.

Schema Evolution Policy

The telemetry schema must be allowed to change without breaking existing publishers, consumers, or stored messages.

  1. New fields should be optional.
  2. Existing default Protobuf field numbers must not be changed or reused.
  3. Deleted enum values, tag numbers, field types, and names must be marked as reserved so no one accidentally reuses them.
  4. Breaking changes require a new major schema package, such as oversight.telemetry.v2.
  5. Consumers must reject unsupported major schema changes.

Proto Best Practices

Mapping Registry

The NIS uses a version-controlled mapping registry to translate protocol-specific data into the Oversight TelemetryEvent contract.

Each mapping must contain the following:

  1. A unique mapping id and version
  2. The approved source endpoint
  3. The source protocol
  4. The protocol-specific source address, such as:
    • Modbus register address
    • OPC UA NodeId
    • Ethernet/IP objects
    • Sparkplug B metric name or alias
  5. Semantic Path
    • Enterprise
    • Site
    • Area
    • Line
    • Asset
    • Tag
  6. The source and data types
  7. Byte order, when required
  8. Scaling factor and offset, when required
  9. Source and engineering units
  10. Expected update interval
  11. Stale-data threshold
  12. Whether the mapping is active or enabled

The mapping must not contain the following:

  1. passwords
  2. certificates
  3. other credentials

The protocol-specific addresses MUST NEVER leave the NIS. The address must remain inside the NIS and must not be included in telemetry published to downstream consumers.

New or updated mappings must be validated before they become active. If validation fails, the NIS continues using the working registry and the previous registry version remains active for rollback.

Changing a device, protocol, or physical address only requires a mapping change.

Connection and Polling Policy

The NIS will only connect to approved OT endpoints. Each endpoint must be included in an allowlist containing its hostname or IP address, port, protocol, and allowed connection settings.

The Oversight NIS will support two telemetry collection methods:

  1. Polling: The NIS requests data from a source over a fixed interval.
  2. Subscription: The NIS subscribes to a source and receives data values that are changed or set at a fixed interval.

Connection & Polling Rules:

  1. All connections must be read-only
  2. Polling and subscription intervals must be able to be configured
  3. The NIS must not poll faster than the approved rate for an endpoint
  4. Each endpoint must have limits for active connections, requests, and subscriptions
  5. Connection and read operations must have timeouts
  6. Failed operations must use a limited number of retries with controlled backoff
  7. Repeated failures must not create an unlimited retry loop or retry storm.
  8. Only one active NIS instance may collect data from an endpoint at one time.
  9. A standby NIS instance must remain passive until ownership handover or the active instance is confirmed unavailable.
  10. Late, failed, or skipped reads must be recorded and reported.
  11. Telemetry not updated before the stale threshold is met must be reported as stale.
  12. The NIS must not present an old value as a new live measurement.

Quality & Timestamping

The NIS must be able to tell downstream consumers whether each telemetry value can be trusted and when the measurement was taken.

Quality Values

Every TelemetryEvent must contain a quality value.

Quality Value Description
GOOD Value received successfully and is current and valid
BAD Value is invalid or should not be used (e.g., stale telemetry, communication failure, or invalid data)
UNCERTAIN Value may be unstable but consumers must use it with caution
UNKNOWN Not enough information for the NIS to determine quality

The NIS must also include a controlled quality_reason value when quality is BAD or UNCERTAIN.

  • COMMUNICATION_FAILURE
  • STALE_DATA
  • CLOCK_SKEW
  • SOURCE_UNCERTAIN
  • SOURCE_BAD
  • OUT_OF_RANGE
  • MALFORMED_VALUE
  • UNKNOWN

Communication Failures and Stale Values

A telemetry point is stale when it has not been updated with the stale_threshold defined in the mapping registry.

When a telemetry point is stale:

  • The NIS must not present the last value as a new live measurement.
  • The previous event_time must remain unchanged.
  • The point must be marked as BAD.
  • The quality_reason must be set to STALE_DATA or COMMUNICATION_FAILURE.
  • The NIS should publish the quality change only once when the point becomes stale.
  • The NIS must report the communication failure through its health and diagnostics metrics.

When communication is restored, the next successful and valid measurement is returned to GOOD.

Timestamp Fields

  1. event_time - the time when the measurement occurred
  2. ingested_at - the time the NIS received the measurement
  3. published_at - the time the event was queued for publication
  4. source_timestamp - the time the source device recorded the measurement (if available)

All timestamps must use UTC.

Timestamp Precedence

The NIS must choose the event_time in the following order of precedence:

  1. A valid source_timestamp supplied by the field device
  2. A valid protocol-server timestamp, such as a PLC or OPC UA server timestamp
  3. The NIS ingested_at timestamp when no other trusted timestamp is available

The event should contain a timestamp_from value showing the source of the timestamp.

  • SOURCE
  • PROTOCOL_SERVER
  • NIS

Clock Skew Detection

The NIS must compare the event_time and ingested_at timestamps to ensure that they are within the clock-skew threshold. If the difference exceeds this threshold:

  • The event is marked UNCERTAIN
  • The quality_reason is set to CLOCK_SKEW
  • The NIS must report the clock skew through its health and diagnostics metrics.

If the source timestamp is invalid or unusable, the NIS must use the ingested_at timestamp as the event_time and set the timestamp_from to NIS.

The NIS must use an approved time sync service.

Out-of-Order Telemetry

  • An event is “out-of-order” when its event_time is older than the previous event for the same telemetry point.
  • Valid out-of-order events may still be published to downstream consumers for historical storage purposes. However, they must be marked as "out-of-order": true.
  • Consumers such as Redis must not replace a newer value with an older out-of-order value.

Replay Identification

Intentionally replayed telemetry must be marked as "is_replay": true

A replay event should do the following: - Receive a new message_id - Preserve the original event_time - Include the original message ID - Set original_message_id to the ID of the original event

When a JetStream acknowledgement is not received, retrying to publish it is not considered a replay. Publication retries use the same message_id as the original event.

Publication Policy

After the NIS creates the TelemetryEvent, it serializes it using Protocol Buffers and publishes it to NATS JetStream.

Telemetry Subject

oversight.telemetry.<enterprise>.<site>.<area>.<line>.<asset>.<tag>

One Point Per Event

The NIS must publish only one TelemetryEvent point per event.

Required NATS Headers

Headers Value
Nats-Msg-Id The events message_id
Content-type application/x-protobuf
Oversight-Schema-Version The schema version of the TelemetryEvent
Oversight-Trace-Id The events trace_id
Oversight-Correlation-Id The events correlation_id
Oversight-Event-Type telemetry

JetStream Publication Acknowledgement

A TelemetryEvent is not considered successfully published until it is acknowledged by NATS JetStream and receives a JetStream PubAck acknowledgement.

The NIS must:

  • publish the serialized TelemetryEvent to the UNS subject
  • Wait for the JetStream acknowledgement (PubAck)
  • Confirm the acknowledgement was successful
  • Record the acknowledgement latency
  • Treat a rejected acknowledgement as a failed publication
  • Retry when an acknowledgement is not received within the configured timeout
  • duplicate_true is a successful publication

Publication Retry Policy

Publication retries must be written to the durable store-and-forward spool before the NIS makes its first publication. If the write fails, the NIS must not attempt publication or report the event as accepted.

After the event is stored in the store-and-forward spool, the NIS publishes it to NATS JetStream. Every publication attempt of the same TelemetryEvent must use the same message_id, subject, serialized payload, and Nats-Msg-Id header.

Immediate rapid retries must be bounded and use controlled backoff. If the retry limit is reached, the NIS must:

  • Keep the event pending inside the durable spool
  • Record the failure and retry count
  • Change its health status to DEGRADED
  • Stop retry attempts
  • Update its health state
  • Retry the pending event during a later recovery cycle using longer controlled backoff
  • Raise an alarm if the failure exceeds the configured duration or spool-depth threshold
  • The NIS must never continuously retry a failed publication.

The NIS must not delete any event from the durable spool, until it receives the JetStream PubAck acknowledgement. Once the event is successfully stored and the PubAck is received, the NIS marks the event as delivered and removes it from the durable spool. The NIS must follow a configured spool-rentention policy.

Spool Retention Policy

The retry cycle is bounded, but the event remains stored safely and can be used for later delivery.

Maximum Payload Size

A complete TelemetryEvent must not exceed 64 KiB (65,536 bytes). Oversight will reject any event that exceeds this size and route the information to the approved telemetry DLQ subject.

Store & Forward Spool

The NIS uses a persistent, disk-backed store-and-forward spool to protect telemetry during outages or publication failures. A validated TelemetryEvent is not considered accepted until it has been successfully committed to the spool. The durable spool is a temporary delivery protection mechanism so that no telemetry is intentionally dropped during a failure.

Each spool record contains the following information:

  • Serialized Protobuf payload
  • Complete NATS subject
  • Required NATS headers
  • Original message_id
  • Original Nats-Msg-Id
  • Spool sequence number
  • Endpoint ownership
  • A checksum or other integrity check
  • A timestamp when the event was committed to the spool
  • Delivery status

The standby NIS must not publish replicated records while the active NIS retains endpoint ownership.

After receiving the PubAck acknowledgement from JetStream the NIS marks the spool record as delivered and the record can be removed from the spool according to the spool-cleanup policy.

If the publication fails or an acknowledgement is not received, the record must stay inside the spool and be retried using the same subject, message_id, and Nats-Msg-Id header.

If replication fails the NIS must:

  • Retain the record locally with an UNREPLICATED delivery status
  • Not fully accept the record, change its replication health state to DEGRADED, and raise an alert.
  • Stop beginning new polls and pause or close subscriptions after the configured grace period.
  • Not delete the record

Failure Modes & Fallbacks

The NIS must fail safely

  • A failure must not cause a field write, equipment state change, or control command.
  • A failure in one adapter must not stop unrelated endpoints from being processed.

Source Unavailable

  • Mark endpoint as unavailable
  • Begin bounded reconnection attempts
  • Mark affected points stale after their configured thresholds are met.

Read Timeout

  • Record the timeout
  • Retry, according to the endpoint policy
  • Do not create a fake measurement

Invalid or Unmapped Source Point

  • Reject observation
  • Send sanitized failure info to the diagnostic or telemetry DLQ subject

Unsupported Data Type

  • Reject only the affected point
  • Increment the rejection counter
  • Allow the adapter to continue processing other points

Invalid Scale, Offset, or Unit

  • Reject the affected mapping
  • Do not publish an incorrectly normalized value

Missing Source Timestamp

  • Use the NIS ingestion time and set timestamp_from to NIS

Invalid or Stale Timestamp

  • Mark the event UNCERTAIN or BAD, depending on the configured timestamp and stale-data rules

Protobuf Serialization Failure

  • Do not publish the invalid event
  • Record the failure
  • Route sanitized diagnostic info to the telemetry DLQ subject

JetStream PubAck Timeout

  • Retry with the same message_id and Nats-Msg-Id header using bounded backoff.

NATS Unavailable

  • Store validated events in the durable store-and-forward spool
  • Attempt controlled connections

Certificate Invalid or Expired

  • Refuse connection
  • Mark the endpoint as unhealthy
  • Generate an alert
  • TLS validation must not be bypassed.

Mapping Reload Failure

  • Continue using the current valid mapping-registry version

Adapter Crash

  • Restart the affected adapter without restarting unrelated adapters when possible

NIS Process Restart

  • Recover pending spooled events
  • Reacquire endpoint ownership
  • Prevent duplicate active pollers

Retries MUST HAVE:

  • A configured maximum attempt count
  • A configured timeout
  • Controlled backoff
  • Jitter to prevent too many endpoints from reconnecting at the same time
  • A health alert after the retries are exhausted

The Durable Spool MUST HAVE:

  • Have a fixed maximum size
  • Survive an ordinary NIS process restart
  • Track its current depth and oldest event age
  • Protect stored data against unauthorized access
  • Never grow without a limit

Security Controls

  1. Read-Only Access: The NIS must only have read-only access to the approved OT endpoints.
  2. NATS Permissions: The NIS must use a dedicated NATS identity.

It must be allowed to:

  • Publish to oversight.telemetry.>
  • Publish NIS health info to its oversight.health.> subject
  • Publish failures to oversight.dlq.telemetry
  • Subscribe to its NATS inbox subjects when required to receive JetStream acknowledgements.

It must not be allowed to:

  • Publish to oversight.commands.>
  • Subscribe to oversight.commands.>
  • Create, Delete, or Change Jetstream streams
  • Access unrelated audit, command, or administrative subjects.

NATS permissions are managed and enforced through the publish and subscribe allowlists.

NATS Authorization Documentation

  1. Transport Security

  2. Use TLS where supported

  3. Validate certificate trust chains, hostnames, and expiration dates
  4. Reject invalid, untrusted, or expired certificates
  5. Never silently disable certificate validation

  6. Use network segmentation and endpoint allowlists for protocols that do not provide native encryption

  7. Endpoint Allowlists

Connections must only be allowed to approved IP addresses, ports, protocols, device identities, MQTT topics, or OPC UA namespaces.

  1. Secret Management

Credentials, private keys, and tokens MUST:

  • Be stored outside the mapping registry and source code
  • Be provided through an approved secret manager
  • Be readable only by the NIS
  • Never appear in logs, metrics, telemetry payloads, or diagnostic events

  • Support rotation without changing telemetry mappings.

  • Input Validation: The NIS must validate all incoming telemetry data.

The NIS must reject the following:

  • Malformed protocol responses
  • Oversized messages
  • Unsupported data types
  • Invalid lengths of register counts
  • Invalid Protobuf events
  • Unapproved topics, NodeIds, object paths, or register ranges

Raw protocol frames and physical addresses must not be exposed to the normal UNS telemetry path.

Observability

The NIS must be able to gather enough information to determine whether telemetry is being received, normalized, and is being published correctly.

The following metrics must be collected and available for monitoring:

The NIS must provide the following:

  • A liveness check showing that the process is running
  • A readiness check showing that the required configuration is valid and the service can publish telemetry
  • Alerts for stale endpoints, repeated failures, high spool usage, publication failures, and certificate expiration.

Adapter States

Each adapter should report one of the following states:

  • STARTING
  • CONNECTING
  • HEALTHY
  • DEGRADED
  • BACKOFF
  • DISCONNECTED
  • STOPPING

Log Structure

Logs must be structured and should include the following fields:

  • Endpoint ID
  • Mapping ID
  • Adapter type
  • Message ID
  • Error Category
  • Retry Count
  • Timestamp

Scaling & High Availability

The Northbound Ingest Service scales in different ways. It assigns different OT endpoints or asset groups to different NIS instances.

Active / Passive Behavior

The NIS is designed to be highly available and uses active/passive ownership.

The standby instance must not connect to or poll the endpoint while the active instance is healthy. When new ownership is acquired, the new owner must perform a health check before reporting the endpoint as healthy.

Failover may occur only after:

  1. The active instance releases ownership
  2. The ownership lease expires
  3. The active instance is confirmed unavailable

Duplicate Prevention

  • The NIS must prevent duplicate active pollers from connecting to the same endpoint.
  • Publication retries must use stable message IDs. Downstream consumers must process the message_id idempotently (e.g., multiple retries of the same event must produce the same message_id).

Partitioning

Endpoints may be partitioned by:

  • Site
  • Area
  • Line
  • Asset
  • Protocol
  • Endpoint Load

A failure on one partition must not affect the other partitions.

Graceful Shutdown

During a planned shutdown, the NIS must:

  1. Stop starting new polls and subscriptions
  2. Finish or cancel active reads within the bounded timeout
  3. Finish normalization of accepted observations
  4. Collect outstanding JetStream acknowledgements
  5. Flush or preserve spooled events
  6. Close field connections
  7. Release endpoint ownership
  8. Exit

The NIS must not release endpoint ownership until all active polls and subscriptions are complete.

Architectural Design Principles

  1. Read-Only: The NIS is a read-only service that observes the field state but never changes it
  2. Protocol Termination: Modbus, OPC UA, Ethernet/IP, and Sparkplug B details stop at the adapter boundary
  3. Semantic Independence: Downstream consumers receive vendor-neutral Oversight telemetry
  4. Telemetry Contract: The NIS normalizes all telemetry into the Oversight TelemetryEvent contract
  5. Strict Serialization: Validated events are serialized using Protocol Buffers
  6. Bounded Behavior: Connections, retries, queues, buffers, and timeouts must have a bounded size (limits)
  7. Durable Store-and-Forward Spool: Events are stored in a persistent durable store-and-forward spool before being published. This protects telemetry during a NATS JetStream outage or publication failure.
  8. Fail-Safe Behavior: Failures must not generate writes or control actions
  9. Single Endpoint Owner: Only one NIS instance may actively poll or subscribe to an endpoint at a time
  10. At-Least-Once Publication: Events may be retried and republished if the original publication fails
  11. Configuration as Code: Endpoint definitions and mappings must be version controlled and validated
  12. Measurable Observation: Failures, dropped data, latency, freshness, and connection state must be measurable
  13. Separation of Responsibilities: The NIS does not perform anomaly detection, command validation, command execution, or physical control
  14. NATS as transport: The UNS subject identifies the semantic telemetry point, while NATS transports and JetStream stores the Protobuf event.

Implementation Details

Runtime Processing

For every source observation, the NIS performs this sequence:

  1. Receives the observation.
  2. Decodes it.
  3. Resolves its mapping.
  4. Normalizes its value, unit, quality, and timestamps.
  5. Constructs and validates the TelemetryEvent.
  6. Constructs and validates the exact NATS subject and headers.
  7. Serializes the event using Protobuf.
  8. Commits the payload, subject, and headers to the durable spool.
  9. Publishes the stored record to JetStream.
  10. Receives and validates the PubAck.
  11. Marks the spool record delivered.
  12. Removes it according to the spool cleanup policy.
  13. Records metrics and health state.

An observation that fails a required stage must not continue to the next stage.

Risks, Tradeoffs, & Alternatives

I considered the following alternatives and tradeoffs during the design process of the Northbound Ingest Service:

  1. Protobuf instead of JSON
    • Benefit: I found that Protobuf is more efficient and has strict schema enforcement. This reduces the risk of malformed telemetry and allows the NIS to validate the telemetry before publishing it.
    • Tradeoff/Risk: Binary payloads are harder for people to read without decoding tools, but I found using binary payloads worth the time to prevent malformed telemetry from being published to downstream consumers.
  2. Custom Oversight TelemetryEvent instead of Sparkplug B internally
  3. Benefit: By using the custom Oversight TelemetryEvent I can keep the internal contract independent of MQTT and Sparkplug B session behavior
  4. Tradeoff/Risk: Oversight must maintain and version its own schema, however, this was the best option for me because it allows me to reuse the existing Oversight TelemetryEvent contract.
  5. One NIS instead of separate adapter services
  6. Benefit: The benefit is simpler deployment, configuration, and initial operation.
  7. Tradeoff/Risk: A process-level failure may affect multiple adapters unless isolation is implemented carefully. Although this risk is low, it is still a tradeoff.
  8. One point per event instead of batching
  9. Benefit: Simpler retries, quality handling, routing, and failure isolation.
  10. Tradeoff/Risk: Produces more NATS messages and slightly more message overhead, however, for Oversight, the benefit of simpler retries and quality handling outweighs the cost of more messages.
  11. Durable Store-and-Forward Spool
  12. Benefit: Protects telemetry during a NATS JetStream outage or publication failure.
  13. Tradeoff/Risk: Introduces additional disk I/O and storage requirements, however, I felt the tradeoff worth it because telemetry protection for the NIS is critical to the success of the system. This also protects the zero-trust architecture and audit trail.
  14. Active/Passive Endpoint Ownership instead of Active/Active Endpoint Ownership
  15. Benefit: Prevents duplicate polling and reduces load on field devices.
  16. Tradeoff/Risk: Failover is slower than active/active operations, but, Oversight is a telemetry system and not a control system, so the slower failover is acceptable.
  17. Configurable Polling Intervals instead of fixed intervals
  18. Benefit: Allows polling to match device and process requirements.
  19. Tradeoff/Risk: Misconfiguration can overload a controller or make telemetry too slow, but, the benefit of configuration intervals for Oversight outweighs the risk because the system is designed to be highly available.
