RFC-001 - Unified Namespace & Messaging Architecture

Author: Amy Mummert

Status: Proposed

Date: 2026-08-31

Target Components: NATS JetStream & Unified Namespace

Background / Context

This RFC outlines the proposed creation of a unified namespace and messaging architecture for Oversight ICS. The Unified Namespace (UNS) provides an event-driven communication layer that connects telemetry producers, streaming analytics, safety validation services, and the Southbound Driver and uses NATS JetStream as the core message broker.

The UNS provides a single source of truth and provides hardware abstraction by providing downstream services with semantic telemetry data that is not tied to any specific register addresses. It connects the data from the control assets (e.g., PLCs, RTUs, and sensors), edge-of-network devices, SCADA, MES, ERP, etc. into one standardized event stream. By using a UNS, Oversight can speed up Industrial Internet of Things (IIoT) and edge systems, by providing a single source of truth for telemetry and commands, leading to a more efficient and effective system.

The system bridges deterministic OT systems with modern AI reasoning and event-driven analytics while maintaining zero-trust safety by implementing strict separation between the following:

  1. Telemetry Ingestion
  2. Telemetry Normalization
  3. Telemetry Transport
  4. Streaming Analytics
  5. Cognitive Reasoning
  6. Safety Validation
  7. Physical Execution

Component Responsibilities

Northbound Ingest Service: Terminates and normalizes raw industrial protocols into Sparkplug B JSON payloads and extracts raw source data. UNS Normalization: Provides a standardized, vendor-agnostic namespace for telemetry and command data. NATS JetStream: Transports, persists, routes, and replays telemetry and commands. Downstream Consumers: Processes the events without needing to know the original protocol or physical register addresses.

Problem Statement

Industrial Control Systems expose data through several protocols, including Modbus, OPC-UA, and Ethernet/IP. These protocols may expose vendor-specific addressing, device-specific naming, data types, units, and quality bits.

If downstream consumers knew this information, Oversight would become tightly coupled to individual control systems and this would create several problems:

  1. Vendor-specific dependencies
  2. Physical Register Address Exposure
  3. Challenging Horizontal Scaling
  4. Tight Coupling Between Cognitive Services and OT
  5. Increased Safety Risk
  6. Challenging Portability Between Plants
  7. Difficult Replay and Forensic Auditing
  8. Increased Sensitivity to Network Latency and Polling Jitter

Oversight therefore requires a messaging architecture that supports the following:

  1. High-throughput telemetry (10,000 points per second)
  2. Low-latency telemetry ingestion and normalization (sub-50ms)
  3. Durable event storage
  4. Replayable telemetry, event, and command history
  5. Subject-Based Routing
  6. Hardware Abstraction
  7. Schema Versioning
  8. Traceability and Forensic Auditing
  9. Controlled access to event subjects

To achieve this, Oversight uses the Unified Namespace (UNS) to abstract the physical register addresses and vendor-specific protocols.

Proposed Solution

The proposed solution is to use NATS JetStream to provide the messaging, persistence, and replay used for implementing the Unified Namespace to enforce strict Command Query Responsibility Segregation (CQRS) allowing high-velocity telemetry to remain separate from control intent execution.

The Read Path (Ingestion & Observation)

Raw industrial protocols are ingested and strictly terminated by the Northbound Ingest Service preventing direct sessions with the field assets. They are then normalized into Sparkplug B JSON payloads containing metadata and integer quality bits (e.g., 192 for “Good”). These normalized payloads are then published to the NATS JetStream message bus (oversight.telemetry.>) and are consumed by the Bytewax Streaming Engine. The Bytewax Streaming Engine performs windowed Z-Score drift detection and at the same time publishes the results to the TimescaleDB telemetry historian (for the 90-day warm tier) and the Redis Hot Cache (for sub-second lookups).

The Write Path (Control Execution)

Control intents and manual overrides are published to the NATS Command Queue oversight.commands.proposed. These commands are sent to be validated by the Level 1.5 Arbitrator, Semantic Gatekeeper, and the TPM 2.0 hardware signer. If the command fails it is routed to oversight.commands.failed, moved into the DLQ, and persisted to the audit log. The fully notarized commands are then handed to the Southbound Driver for execution, which then publishes the results to oversight.commands.executed.

Unified Namespace (UNS) Information Model

IEC 62264 Hierarchical Topic Structure

Oversight strictly follows the IEC 62264 enterprise standard for topic structure with NATS dot notation to route data.

Format

Enterprise.Site.Area.Line.Asset.Tag

Example

AcmeCorp.Longview_Plant.WaterTreatment.Filtration.Pump_01.Discharge_Pressure

UNS elements for Oversight ICS should:

  • Be deterministic
  • Be unique within their hierarchy
  • Use consistent naming conventions
  • Avoid physical protocol addresses or vendor-specific protocols
  • Be versioned and schema-compliant
  • Be traceable, auditable, immutable, and replayable
  • Be hardware-agnostic
  • Be horizontally scalable
  • Be resilient to network partitions, service address, network jitter, network latency, polling jitter, packet loss, and blocking cyclic scan loops
  • Remain stable when the source protocol changes

Non-Goals

  • PLC control logic
  • SIS safety logic
  • physical actuator behavior
  • Southbound protocol implementation
  • command arbitration algorithms
  • semantic gatekeeper implementation
  • TPM 2.0 hardware signer implementation
  • LangGraph reasoning workflows
  • Bytewax anomaly detection algorithms
  • TimescaleDB historian schema
  • Redis Cache implementation
  • RAG/pgVector implementation
  • WORM/audit storage implementation
  • regulatory retention requirements

Architectural Design Principles

Semantic Independence

Downstream consumers must not know the physical register addresses or vendor-specific protocols. Instead, the UNS provides a semantic namespace that abstracts the physical register addresses and vendor-specific protocols.

The following are examples of physical register addresses and vendor-specific protocols that must not be exposed to downstream consumers:

  • Modbus register addresses
  • OPC-UA node identifiers
  • Ethernet/IP object addresses
  • Vendor-specific device naming

Transport Independence

The event contract must remain decoupled from the NATS JetStream implementation details

Idempotent Command Enforcement

  • Oversight uses At-Least-Once command delivery using NATS JetStream durable consumers and acknowledgements.
  • Each command carries a command_id (UUIDv4) that is used to ensure idempotency to prevent duplicate executions.

Distributed Tracing

The trace_id (UUIDv4) that propagates from the LangGraph Agent is injected into the NATS JetStream message headers of the Command Queue and the Southbound Driver’s execution payload (a live traveling metadata tag).

Command Time-to-Live (TTL)

Every intent published to the NATS Command Queue carries a strict command ttl. If a command is delayed by network jitter, it expires in the queue rather than executing a stale action seconds later.

Message Durability

Using NATS JetStream provides persistent storage, replay, acknowledgements, recovery of published messages, and consumer state tracking. The Oversight system uses a configured retention and replication policy to provide message durability and recovery. Message durability in the system is dependent on the configuration of storage, replication, retention, and acknowledgement policies. Unacknowledged commands may be redelivered to consumers based on the JetStream consumer acknowledgement and redelivery policies.

Latency Targets

  • Field Asset-to-UNS (NATS JetStream UNS): < 50 ms – This is measured from receipt of telemetry by the Northbound Ingest Service to the successful publishing of the event to NATS JetStream.
  • NATS Transport Latency: This is measured from the publisher timestamp to the consumer receipt timestamp.
  • NATS to Bytewax: < 20 ms - This is measured from NATS JetStream consumer receipt of the event to the start of Bytewax processing.
  • End-to-End Latency: This is measured separately from the original telemetry source timestamp. This happens through the application downstream processing or execution stage.

Dead Letter Queue (DLQ)

Oversight implements a dead letter queue (DLQ) using NATS subjects, JetStream streams and consumers, retry policies, and application-level failure handling.

Because NATS does not have a separate broker-level DLQ object, Oversight implements DLQ handling using NATS subjects, and application-level failure handling.

A message may be redirected to a DLQ when it cannot be successfully processed. This happens after the configured retry policy has been exceeded or when the system determines that further processing must be stopped.

DLQ Handling is separated by message type:

  1. Telemetry Processing Failure: Telemetry messages that cannot be processed after the retry policy is exceeded, may be redirected to the DLQ: oversight.telemetry.dlq
    • Examples: Schema validation failure, payload inconsistency, unsupported schema version, invalid event structure Repeated consumer processing failure.
    • Telemetry DLQ messages must be retained for diagnostics, replay analysis, and developer forensics.
    • A telemetry processing failure MUST NOT result in control-affecting commands.
  2. Event Processing Failure: Events that cannot be processed after the retry policy is exceeded may be redirected to: oversight.events.dlq
    • Examples: invalid event schema, unsupported event type, invalid event metadata, repeated consumer processing failure, failure to process a system-generated event.
    • Like Telemetry DLQ messages, event processing messages must be retained for diagnostics, replay analysis, and developer forensics.
    • An event processing failure MUST NOT result in control-affecting commands.
  3. Command Processing Failure: Commands that fail validation or execution may be redirected to: oversight.commands.failed.
    • Examples: Command validation failure, safety validation failure, auth failure, expired command, safety validation failure, duplicate command, Southbound execution failure, physical state verification failure.
    • Command DLQ messages must be retained for audit and operator reviews.
    • A command processing failure MUST NOT result in control-affecting commands.
    • Failed or rejected commands MUST NOT be retried.

Consumer Flow Control (Backpressure Management)

By using NATS consumer pull-model flow control, the system prevents the Agent from being overwhelmed by telemetry bursts. This lets the Broker buffer the load while the reasoning engine completes its inference cycle.

Health Metrics

Tracks system-level KPIs via NATS Consumer Lag If backpressure rises, Prometheus triggers a System Health alert before telemetry data is dropped.

Data Storm Resilience (NATS Buffer)

During telemetry surges or “Data Storms,” the Northbound Ingest Service publishes telemetry to JetStream, where persistent storage provides buffering and replay capability. This prevents memory exhaustion and protects the NATS Command Queue from being overwhelmed.

Horizontal Scaling

The system can horizontally scale using NATS durable consumers. Where appropriate, queue-groups and/or shared consumer patterns can be used to distribute processing across multiple consumers.

Fail-Safe “HOLD” Mode

In the event of a heartbeat failure, the system will prevent control-affecting commands from being executed in the NATS Command Queue and issues a WATCHDOG_TRIP alarm.

Failure Modes & Fallbacks

NATS Telemetry Stream Stale / Idle Timeout (Zero-Tolerance Watchdog)

If the NATS consumer detects the absence of expected telemetry, the system will trigger a dedicated NATS Watcher service which publishes a STALE_DATA event.

Middleware Integrity Watchdog (Fail-Safe “HOLD” Mode)

The Southbound Driver actively monitors the LangGraph Agent’s heartbeat via the NATS JetStream KV bucket. If the Agent’s timestamp becomes stale, the system will prevent control-affecting commands from being executed in the NATS Command Queue and issues a WATCHDOG_TRIP alarm.

NATS Message Broker Latency

  • The Oversight system MUST monitor NATS message latency for time-sensitive message flows.
  • NATS message latency MUST be measured using message timestamps and consumer receipt timestamps for application level time-sensitive message flows.
  • The system MUST be able to distinguish between NATS transport latency and consumer processing delays.
  • Latency MUST be monitored against the defined thresholds. Thresholds are appropriately defined based on message type and operational requirements.
  • The system MUST treat the message flow as degraded when latency exceeds the defined thresholds.
  • Latency MUST NOT result in autonomous physical actuation.
  • The system MUST log latency events and alert the operator when the threshold is exceeded.
  • Normal message flow MUST NOT resume based on latency decreases. Recovery MUST require health verification.

The following defines each latency measurement in the system: 1. Ingest Latency: Time from receipt of source telemetry by the Northbound Ingest to successful publishing of the event to NATS JetStream. 2. NATS Transport Latency: Time from the publisher timestamp to the consumer receipt timestamp. 3. Consumer Processing Latency: Time from consumer receipt of a message to completion of the downstream processing. 4. End-to-End Latency: Time from the originating event or telemetry timestamp through the application level downstream processing or execution stage.

Consumer Lag MUST NOT be treated as equivalent to NATS transport latency.

NATS Command TTL Expiry

  • Every control-affecting command MUST have an application level expiration timestamp.
  • An expired command MUST NOT be executed.
  • Commands MUST contain the following (at minimum):
    • command_id - command ID (UUIDv4)
    • created_at - command creation timestamp
    • expires_at - the time after which the command is no longer valid.
  • A command is only valid while the current time is less than the expires_at timestamp.
  • Command expiration MUST be enforced by the Southbound Driver before control-affecting commands are allowed.
  • Command validation MUST be performed before control-affecting commands are allowed.
  • If the current time is greater than or equal to the expires_at timestamp, the command MUST be marked as EXPIRED and control-affecting commands MUST NOT be allowed.
  • If a command is expired, the system MUST NOT try to retry or reissue automatically.
  • The system MUST log the command expiration, including the command_id, created_at and expires_at timestamps and the expiration reason.
  • The system MUST alert the operator when command execution affects control operations.
  • Expiration of a command MUST NOT result in control-affecting commands being issued or authorized.

NATS Connection Failure

The Oversight system treats NATS and JetStream as non-authoritative.

  • Failure or unavailability of NATS or JetStream MUST NOT cause Oversight to issue or authorize a new control-affecting command.
  • Loss of NATS connectivity is required to be treated as a degraded state, and the system MUST enter degraded authority mode.
  • The control assets and safety systems remain responsible for the local control and safety behavior.

Bounded Retries

  • Connection attempts MUST be bounded to prevent retry storms.
  • Repeated connection failures are required to contribute to the circuit breaker failure threshold.
  • Once the failure threshold is reached, the circuit breaker MUST prevent repeated connection attempts. Connection attempts can only be resumed after the recovery conditions are met.

Health Verification

  • Recovery MUST require successful health verification before normal message flow resumes.
  • Recovery MUST NOT automatically restore normal message flow.
  • After the reset timeout expires, the circuit breaker MUST transition from OPEN to HALF_OPEN and permit a limited recovery attempt.
  • Normal message flow MUST resume only after successful health verification.
  • A failed recovery attempt MUST transition the circuit back to OPEN.

Logging and Operator Alerting

  • The system MUST log the NATS failures, circuit breaker transitions, recovery attempts, and recovery failures.
  • The system MUST alert the operator when NATS availability affects normal operations or causes a transition to the degraded authority mode.

NATS Circuit Breaker

The Oversight system uses a circuit breaker to prevent continuous attempts against a failing NATS dependency.

  • Services that depend on NATS MUST implement the NATS circuit breaker to stop the circuit breaker from making repeated connection attempts after the configured failure threshold is reached.

CLOSED

  • Normal operation.
  • The system is healthy and NATS is available.

OPEN

  • The failure threshold is reached.
  • NATS operations MUST fail fast
  • Repeated connection attempts are blocked.
  • Dependent services MUST remain in Degraded Authority Mode.

HALF-OPEN

  • After the reset timeout expires, a limited recovery attempt is permitted. This is to determine if NATS has recovered.
  • The limited recovery attempt will determine whether NATS has recovered enough to allow normal message flow.
  • Successful health verification MUST transition the circuit breaker from HALF-OPEN to CLOSED.
  • Failed health verifications MUST transition the circuit breaker back to OPEN.

Degraded Authority Mode

  • Dependent services MUST inhibit new control-affecting commands when NATS is unavailable or degraded.
  • The appropriate degraded authority mode MUST be reached according to Oversight’s control authority model.
  • Physical fail-safe behavior (fail-closed, fail-open, fail-trip, hold-last-state, or other safe state behavior) MUST NOT be determined by the NATS circuit breaker.
  • Local control assets and safe-state behavior remain responsible for their defined normal control, local safe-state, and safety trip conditions.

NATS JetStream Subject Routing

To enforce strict routing between the Read and Write paths, the broker will enforce the following contracts/namespaces:

Subject Description Primary Producers Primary Consumers
oversight.telemetry.> Telemetry events Northbound Ingest Bytewax, Historian, Redis
oversight.commands.> Command lifecycle events Agent, UI, Arbitrator Southbound Driver, Audit
oversight.events.> System generated events Platform / Analytics Platform services, Audit
oversight.audit.> Audit events and audit-event messages System Components Audit Pipeline
oversight.health.> Health & Watchdog events Platform Services Monitoring / Operations

Telemetry Subjects

oversight.telemetry.> is the subject for all telemetry events.

The subject must not contain physical register addresses or vendor-specific protocols.

Event Subjects

oversight.events.> is the subject for all system-generated events.

Examples:

  1. oversight.events.failover
  2. oversight.events.alarm
  3. oversight.events.status
  4. oversight.events.drift
  5. oversight.events.loss_of_signal
  6. oversight.events.state_change
  7. oversight.events.manual_override

oversight.commands.> is the subject for all proposed commands.

Examples:

  1. oversight.commands.proposed
  2. oversight.commands.validated
  3. oversight.commands.executed
  4. oversight.commands.failed
  5. oversight.commands.rejected

Message Broker Tradeoffs, Drawbacks, and Alternatives: NATS JetStream vs. Kafka vs. RabbitMQ

I chose NATS JetStream as the message broker for the telemetry stream and command queue, instead of RabbitMQ or a standard MQTT Broker (Mosquitto) or Kafka. NATS JetStream provides a high-performance, lightweight messaging system that is appropriate for the high-velocity telemetry data in an OT environment. NATS JetStream offers lightweight connectivity, low latency, and built-in support for message persistence and replay. These are all critical for the real-time monitoring and control requirements of the system.

Tradeoff

For this specific use case, the simplicity and performance of NATS JetStream make it the best fit for the high-throughput time-series telemetry and command messaging needs of the system.

I also considered Kafka, RabbitMQ, and Mosquitto as potential message brokers, but found them to be too complex and/or expensive for this use case. One thing I found with RabbitMQ was that it is not designed for high-throughput time-series data, which is a hard no for the Oversight system. It also consumes and then removes messages, which is not suitable for the command queue and audits. Kafka, on the other hand, does handle high-throughput time-series data very well. However, it would introduce greater complexity than required for the Oversight system.

NATS JetStream provides me a simpler, more lightweight solution that still meets the performance and reliability requirements of the Oversight system without introducing unnecessary complexity and cost.

Implementation Plan

Phase 1: Broker & NATS JetSream Configuration

  1. Deploy NATS JetStream on the Level 3.5 IDMZ.
  2. Enable JetStream
  3. Configure persistent storage for the telemetry and command queues.
  4. Configure Authentication & Authorization.
  5. Establish Health Monitoring.
  6. Configure NATS JetStream durable consumers and DLQ.
  7. Configure JetStream retention, replication, storage, and consumer acknowledgement policies.
  8. Implement Failure Modes:
    • If downstream consumer latency or backpressure is too high and exceeds safe execution limits, NATS will manage buffer saturation with consumer pull-models and Linux Cgroups. Stream silence means the system will trigger the Zero-Tolerance Watchdog to inhibit AI writes.

Phase 2: UNS Contract

  1. Define the semantic hierarchy of the UNS.
  2. Define Telemetry, Event, and Command Subjects.
  3. Define schema versioning.
  4. Define UNS rules
    • Rule 1: No physical register addresses or vendor-specific protocols in the UNS.
    • Rule 2: All telemetry and command events must be traceable, auditable, immutable, and replayable.
    • Rule 3: Protocol changes must not change the semantic identity.
    • Rule 4: Namespace names are deterministic and unique.
    • Rule 5: Mappings are version-controlled and schema-compliant.
  5. Map raw vendor registers to the ISA-95 / IEC 62264 UNS namespace. The topic structure will be AcmeCorp.Longview_Plant.WaterTreatment.Filtration.Pump_01.Discharge_Pressure. This occurs via tag dictionary lookup / uns mapping where raw data is translated into the Sparkplug B payloads needed for the system.

Phase 3: Stream Configuration

  1. Create stream configuration (telemetry, event, command, and audit) in NATS JetStream
  2. Configure command expiration
  3. Configure durable consumers and DLQ
  4. Configure JetStream retention, replication, storage, and consumer acknowledgement policies
  5. Implement pull consumers where necessary to handle backpressure.
  6. Implement consumer failover and workload redistribution using queue groups/shared consumers.
  7. Configure acknowledgement behavior.
  8. Configure consumers
  9. Implement idempotency

Phase 4: Security & Operational Configuration

  1. Create NATS identities
  2. Apply least-privilege access control to the NATS identities
  3. Enable authentication and authorization
  4. Enable TLS

Phase 5: Validation, Stress, and Fallback Testing

  1. Execute integration tests to verify that the stream publishes, the subscriber consumes the messages, and consumer failover and workload redistribution are functioning correctly.
  2. Simulate network partitions, stream silence, and sequence number skips to test the Zero-Tolerance Watchdog, which should inhibit AI writes and trigger safe-state logging.
  3. Conduct backpressure testing using Linux Cgroups and NATS pull-consumer models, which prevents stream saturation from degrading Level 1 deterministic control loops.

Risks & Security Considerations

  1. Security: The system is designed to operate within a Level 3.5 IDMZ/Edge environment. All NATS communications must use TLS where applicable and JetStream storage must be protected. The system uses TPM 2.0 for hardware-based key storage and signing of commands. All commands are validated and authenticated before execution.
  2. Risks:
  3. Single Point of Failure: The NATS JetStream broker is a critical component. If it fails, telemetry and command messaging will be disrupted.
    • To mitigate, use a clustered NATS deployment with failover.
  4. Latency: High latency in the command queue could lead to delayed execution of control intents.
    • To mitigate, monitor latency and implement backpressure handling.
  5. Data Loss: In the event of a crash, there is a risk of losing unprocessed messages.
    • To mitigate, use persistent storage and replay capabilities of NATS JetStream.

Impact and Benefits

Area Impact Benefit
Hardware Abstraction Decouples AI Agent and UI Dashboards from the Level 1 register addresses Allows the system to be hardware and vendor-agnostic. It remains horizontally scalable across multiple-brand industrial plants without rewriting code.
CQRS Isolation Strict separation of high-velocity telemetry (read path) from the command path (write path) Prevents compromising physical safety and deterministic timing of the Level 1 control loops.
Forensic Traceability Provides a distributed log that is WORM compliant for every telemetry frame and command transition Full auditability and step-by-step reasoning replays of every command and telemetry frame for ISA 18.2, NERC CIP, and EPA regulatory compliance.
Sub-50ms Latency Target Ingests and normalizes telemetry into the NATS UNS within a sub-50ms latency target Prevents network jitter or blocking cyclic scan loops during delivery of high-velocity telemetry processing.
Edge Autonomy Broker, stream engine, and command queues are inside the Level 3.5 IDMZ/Edge. Maintains full autonomy and safe-state control even during the loss of internet connectivity.

Conclusion

By choosing NATS JetStream as the message broker, I have achieved the following:

  • Meets the strict CQRS architecture requirements
  • Provides hardware abstraction by keeping the cognitive reasoning layer from knowing the physical register addresses. This also allows for the system to be hardware-agnostic.
  • NATS JetStream is lightweight and provides persistent, replayable messaging with the ability to configure retention, acknowledgements, and consumer recovery.
  • The Level 3.5 IDMZ/Edge maintains full autonomy and safe-state control even during loss of internet connectivity.
