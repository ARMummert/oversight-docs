RFC-001 - Unified Namespace & Messaging Architecture

Author: Amy Mummert

Status: Proposed

Date: 2026-08-31

Target Components: NATS JetStream & Unified Namespace

Background / Context

This RFC outlines the proposed creation of a unified namespace and messaging architecture for Oversight ICS. The Unified Namespace (UNS) provides event-driven communication that connects telemetry to AI Agent orchestration, streaming analytics, safety validation services, and the Southbound Driver and uses NATS JetStream as the core message broker.

The UNS provides a single source of truth and an event layer connecting Telemetry producers, streaming analytics, cognitive reasoning, safety validation, and the Southbound Driver. It also provides hardware abstraction by providing downstream services with semantic telemetry data that is not tied to any specific register addresses. It connects the data from the control assets (e.g., PLCs, RTUs, and sensors), edge-of-network devices, SCADA, MES, ERP, etc. into one standardized event stream. A UNS can also speed up Industrial Internet of Things (IIoT) and edge systems, by providing a single source of truth for telemetry and commands, leading to a more efficient and effective system.

The system bridges deterministic OT systems with modern AI reasoning and event-driven analytics while maintaining zero-trust safety by implementing strict separation between the following:

  1. Telemetry Ingestion
  2. Telemetry Normalization
  3. Telemetry Transport
  4. Streaming Analytics
  5. Cognitive Reasoning
  6. Safety Validation
  7. Physical Execution

The Northbound Ingest Service terminates and normalizes the raw industrial protocols, while the Southbound Driver is the only component authorized to communicate with control assets. The UNS therefore provides an event layer between these components.

Northbound Ingest Service: Terminates and normalizes raw industrial protocols into Sparkplug B JSON payloads and extracts raw source data. UNS Normalization: Provides a standardized, vendor-agnostic namespace for telemetry and command data. NATS JetStream: Transports, persists, routes, and replays telemetry and commands. Downstream Consumers: Processes the events without needing to know the original protocol or physical register addresses.

Problem Statement

Industrial Control Systems (ICS) expose data through several protocols, including Modbus, OPC_UA, and Ethernet/IP. These protocols are often vendor-specific and expose physical register addresses.

The Oversight system must be able to ingest high-throughput telemetry (often exceeding 10,000 points per second) from the deterministic control layers (0–2). If downstream consumers knew the specific physical register addresses or vendor-specific protocols, it would create several problems:

  • Vendor-specific dependencies
  • Physical Register Address Exposure
  • Challenging Horizontal Scaling
  • Tight Coupling Between AI Agent and Level 1 Control Loops
  • Increased Safety Risk
  • Difficult Replay and Forensic Auditing
  • Increased Sensitivity to Network Latency and Polling Jitter

Oversight requires a messaging architecture that supports the following:

  1. High-throughput telemetry (10,000 points per second)
  2. Low-latency telemetry ingestion and normalization (sub-50ms)
  3. Durable event storage
  4. Replayable telemetry and command history
  5. Subject-Based Routing
  6. Hardware Abstraction
  7. Schema Versioning
  8. Traceability and Forensic Auditing
  9. Zero-Command Loss
  10. Controlled access to event subjects

To achieve this, Oversight uses the Unified Namespace (UNS) to abstract the physical register addresses and vendor-specific protocols.

Architectural Design

Oversight will use NATS JetStream as the messaging component for the Unified Namespace. The data flow is as follows:

Source Protocol → Northbound Ingest → UNS Normalization → NATS JetStream → Downstream Consumers

Responsibility Boundary

Responsibility Owner

Define event structure UNS
Define subject naming conventions UNS

Note

The core problem is ingesting telemetry without exposing the physical register addresses to the AI Agent. Even though the Northbound Ingest Service is responsible for normalizing the raw industrial protocols, the UNS defines what the data means and NATS transports that data.

Proposed Solution

The proposed solution is to use NATS JetStream as the internal messaging component for the Unified Namespace. The benefits of this approach are:

  1. Easy lookups and routing by subject.
  2. Naming conventions and hierarchical subjects are easy to integrate with data across different devices and vendors.
  3. Using tools like MQTT and Sparkplug B to make data ingestion and normalization easier.
  4. Do not need to know the physical register addresses or vendor-specific protocols.
  5. A single source of truth for telemetry and commands.
  6. Provides a WORM-compliant, append-only log for every telemetry frame and command transition.
  7. Reduced Complexity and Cost.

Data Flow

The Read Path (Ingestion & Observation)

Raw industrial protocols are ingested and normalized by the Northbound Ingest Service into Sparkplug B JSON payloads containing metadata and integer quality bits (e.g., 192 for “Good”). They are strictly terminated by the Northbound Ingest Service to prevent direct sessions with field assets. These normalized payloads are then published to the NATS JetStream message bus (oversight.telemetry.>) and are consumed by the Bytewax Streaming Engine. The Bytewax Streaming Engine performs windowed Z-Score drift detection and publishes the results to the TimescaleDB telemetry historian (for the 90-day warm tier) and the Redis Hot Cache (for sub-second lookups).

The Write Path

Control intents and manual overrides are published to the NATS Command Queue (oversight.commands.proposed). These commands are sent to be validated by the Level 1.5 Arbitrator, Semantic Gatekeeper, and the TPM 2.0 hardware signer. The fully notarized commands are then handed to the Southbound Driver (translates the payload into raw wire data) and pushes it through the Southbound Firewall.

Unified Namespace (UNS) Information Model

IEC 62264 Hierarchical Topic Structure

Oversight strictly follows the IEC 62264 enterprise standard for topic structure with NATS dot notation to route data.

Format

Enterprise.Site.Area.Line.Tag

Example

AcmeCorp.Longview_Plant.WaterTreatment.Filtration.Pump_01.Discharge_Pressure

UNS elements should:

  • Be deterministic
  • Be unique within their hierarchy
  • Use consistent naming conventions
  • Avoid physical protocol addresses or vendor-specific protocols
  • Be versioned and schema-compliant
  • Be traceable and auditable
  • Be immutable and replayable
  • Be hardware-agnostic
  • Be horizontally scalable
  • Be resilient to network partitions, service address, network jitter, network latency, polling jitter, packet loss, and blocking cyclic scan loops
  • Remain stable when the source protocol changes

NATS Subject Contracts

To enforce strict routing between the Read and Write paths, the broker will enforce the following contracts/namespaces:

Subject Description Processing Component Data Flow
oversight.telemetry.> UNS telemetry events normalized from various sources Northbound Ingest / UNS Read Path
oversight.commands.proposed AI or Operator intents awaiting safety validation Level 1.5 Arbitrator Write Path
oversight.commands.validated Commands that passed the Semantic Gatekeeper & TPM 2.0 Semantic Gatekeeper & TPM 2.0 Write Path
oversight.commands.executed Commands executed by the Southbound Driver Southbound Driver Write Path
oversight.commands.failed Rejected Intents, logged for forensic audit DLQ & WORM & Southbound failure handling Write Path
oversight.events.failover System generated failover events LangGraph Agent & Bytewax Events
oversight.audit.> WORM Compliant forensic auditing TimescaleDB & LGTM Stack Audit
oversight.health.> Health and operational status events for Oversight services Platform Service Monitoring Health

Message Broker Tradeoffs, Drawbacks, and Alternatives: NATS JetStream vs. Kafka vs. RabbitMQ

I chose NATS JetStream as the message broker for the telemetry stream and command queue, instead of RabbitMQ or a standard MQTT Broker (Mosquitto) or Kafka. NATS JetStream provides a high-performance, lightweight messaging system that is appropriate for the high-velocity telemetry data in an OT environment. NATS JetStream offers lightweight connectivity, low latency, and built-in support for message persistence and replay. These are all critical for the real-time monitoring and control requirements of the system.

Tradeoff

For this specific use case, the simplicity and performance of NATS JetStream make it the best fit for the high-throughput time-series telemetry and command messaging needs of the system.

I also considered Kafka, RabbitMQ, and Mosquitto as potential message brokers, but found them to be too complex and/or expensive for this use case. One thing I found with RabbitMQ was that it is not designed for high-throughput time-series data, which is a hard no for the Oversight system. It also deletes messages once consumed, which is not suitable for the command queue and audiits. Kafka, on the other hand, does handle high-throughput time-series data very well. However, it would not be cost-effective as a solo developer to use it and requires more setup, maintenance, and expertise.

NATS JetStream provides me a simpler, more lightweight solution that still meets the performance and reliability requirements of the Oversight system without introducing unnecessary complexity and cost.

Implementation Plan

Phase 1: Broker & NATS JetSream Configuration

  1. Establish a NATS JetStream cluster on the Level 3.5 IDMZ dual-homed IPC using disk-backed storage. This is for at-least-once processing of messages.
  2. NATS Subjects:
    • Telemetry: oversight.telemetry.>
    • Commands: oversight.commands.proposed, oversight.commands.validated, oversight.commands.executed, oversight.commands.failed
    • Events & Audits: oversight.events.failover, oversight.audit.>
  3. Payload Standards: Sparkplug B JSON with standard metadata and integer quality bits (e.g., 192 for good)
  4. Configure consumer offset tracking and Write Once Read Many (WORM) retention policies to enforce the at-least-once processing of messages.
  5. Failure Modes:
    • If downstream consumer latency or backpressure is too high and exceeds safe execution limits, NATS will manage buffer saturation with consumer pull-models and Linux Cgroups. Stream silence means the system will trigger the Zero-Tolerance Watchdog to inhibit AI writes.

Phase 2: Northbound Ingest Service & UNS Mapping

  1. Deploy the Northbound Ingest Service to normalize raw industrial protocols into Sparkplug B JSON payloads. This terminates the raw session data at the Level 3.5 IDMZ.
  2. Map raw vendor registers to the ISA-95 / IEC 62264 UNS namespace. The topic structure will be AcmeCorp.Longview_Plant.WaterTreatment.Filtration.Pump_01.Discharge_Pressure. This occurs via tag dictionary lookup / uns mapping where raw data is translated into the Sparkplug B payloads needed for the system.
  3. Enforce Sparkplug B JSON payloads to be validated by the Northbound Ingest Service. This will ensure that the payloads are in the correct format and contain the necessary metadata, like integer quality bits (e.g., 192 for good) before publishing to oversight.telemetry.>.

Phase 3: Stream Consumer Integration (Read Path)

  1. Connect the Bytewax Streaming Engine to the NATS JetStream telemetry stream (oversight.telemetry.>). The Bytewax streaming engine is the consumer group subscribing to the telemetry topic.
  2. Route Bytewax outputs concurrently to the Redis Hot Cache and TimescaleDB telemetry historian.

Phase 4: Command Queue Integration (Write Path)

  1. Connect the Level 1.5 Arbitrator to the NATS JetStream command queue (oversight.commands.proposed). The Arbitrator will enforce the Two-Key Multi-Factor Authentication (2-MFA) for the proposed commands.
  2. Connect the Level 1.5 Arbitrator to the Semantic Gatekeeper for physical bounds checking and the TPM 2.0 hardware signer for the signed commands. This routes the approved payloads to oversight.commands.validated.
  3. Connect the Southbound Driver to oversight.commands.validated for execution. The Southbound Driver publishes the completion status to oversight.commands.executed or oversight.commands.failed.

Phase 5: Validation, Stress, and Fallback Testing

  1. Execute integration tests to verify that the stream publishes, the subscriber consumes the messages, and consumer group rebalancing is tracked correctly.
  2. Simulate network partitions, stream silence, and sequence number skips to test the Zero-Tolerance Watchdog, which should inhibit AI writes and trigger safe-state logging.
  3. Conduct backpressure testing using Linux Cgroups and NATS pull-consumer models, which prevents stream saturation from degrading Level 1 deterministic control loops.

Risks & Security Considerations

  1. Security: The system is designed to operate within a Level 3.5 IDMZ/Edge environment. All data is encrypted at rest and in transit. The system uses TPM 2.0 for hardware-based key storage and signing of commands. All commands are validated and authenticated before execution.
  2. Risks:
  3. Single Point of Failure: The NATS JetStream broker is a critical component. If it fails, telemetry and command messaging will be disrupted.
    • To mitigate, use a clustered NATS deployment with failover.
  4. Latency: High latency in the command queue could lead to delayed execution of control intents.
    • To mitigate, monitor latency and implement backpressure handling.
  5. Data Loss: In the event of a crash, there is a risk of losing unprocessed messages.
    • To mitigate, use persistent storage and replay capabilities of NATS JetStream.

Impact and Benefits

Area Impact Benefit
Hardware Abstraction Decouples AI Agent and UI Dashboards from the Level 1 register addresses Allows the system to be hardware and vender-agnostic. It remains horizontally scalable across multiple-brand industrial plants without rewriting code.
CQRS Isolation Strict separation of high-velocity telemetry (read path) from the command path (write path) Prevents compromising physical safety and deterministic timing of the Level 1 control loops.
Forensic Traceability Provides and append-only, WORM-compliant log for every telemetry frame and command transition Full auditability and step-by-step reasoning replays of every command and telemetry frame for ISA 18.2, NERC CIP, and EPA regulatory compliance.
Sub-50ms Latency Target Ingests and normalizes telemetry into the NATS UNS within a sub-50ms latency target Prevents network jitter or blocking cyclic scan loops during delivery of high-velocity telemetry processing.
Edge Autonomy Broker, stream engine, and command queues are inside the Level 3.5 IDMZ/Edge. Maintains full autonomy and safe-state control even during the loss of internet connectivity.
Zero Command Loss Stream sequence offsets are replaceable to allow the recovery of drivers to reboot and request missed messages. Prevents command dropping during unexpected service outages or IPC power cycles.

Conclusion

By choosing NATS JetStream as the message broker, I have achieved the following:

  • Fulfills the strict CQRS architecture requirements
  • Provides hardware abstraction by keeping the AI Agent from knowing the physical register addresses. This also allows for the system to be hardware-agnostic.
  • NATS JetStream is lightweight and provides an immutable, append-only distributed log. This allows for every telemetry frame and proposed command to be traceable and forensically auditable.
  • The Level 3.5 IDMZ/Edge maintains full autonomy and safe-state control even during loss of internet connectivity.
