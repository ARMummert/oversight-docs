RFC-002 - Northbound Ingest Service & Protocol Normalization

Author: Amy Mummert

Status: Proposed

Date: 2026-09-01

Target Components: Northbound Ingest Service, Protocol Adapters, Protocol Normalization, Telemetry Mapping

Background / Context

This RFC defines the proposed design and operation of the Northbound Ingest Service (NIS) and the protocol normalization pipeline.

The Oversight system relies on strict separation between OT environments and IT environments. Telemetry must move northbound from the field assets and control assets into the Level 3.5 demilitarized zone without allowing downstream consumers to establish direct connections to those assets.

Field assets, PLCs, RTUs, gateways, and supervisory systems may expose telemetry through a variety of protocols (e.g., Modbus, OPC-UA, Ethernet/IP, MQTT/Sparkplug-B). Each source protocol processes information differently:

  • Modbus TCP:
  • Process data - coils, discrete inputs, input registers, and holding registers
  • Accessed using function codes and addresses.
  • OPC-UA:
  • Typed process values – accessed through an information model containing variables and other nodes using NodeIds.
  • A returned value may contain a value, source timestamps, server timestamps, and status codes.
  • Ethernet/IP:
  • Implements the CIP (Common Industrial Protocol) using objects, instances, attributes, assemblies, and explicit or implicit messaging
  • MQTT / Sparkplug-B:
  • Industrial process metrics using the Sparkplug B MQTT topic namespace, payload model, and state management (such as birth and death notifications)

These protocols are not suitable for the internal telemetry contract for Oversight. Allowing downstream consumers to have direct access to these protocols would tightly couple Oversight to the individual industrial protocols. This would expose raw protocol-specific information to downstream consumers. This presents a security risk and increases the complexity of the system.

Problem Statement

Oversight ICS is designed to ingest high-throughput telemetry exceeding 10,000 points per second from the deterministic control layers. The Northbound Ingest Service must communicate with industrial protocols, however, to remain secure, protocol-specific information must be terminated at the ingestion boundary and must not be exposed directly to downstream consumers.

If we were to allow downstream consumers (Bytwax, TimescaleDB, Redis, LangGraph Agent) to consume the protocol-specific data directly, this would tightly couple Oversight to individual industrial protocols.

Without protocol normalization, every downstream consumer would need to understand those raw industrial protocols, which increases the attack surface and is a huge safety risk. This would also reduce hardware abstraction and increase the complexity of the system.

In addition, unmanaged polling, subscription, or connection behavior against field controllers can introduce an excessive load on the system.

Proposed Solution

The proposed solution is to implement the Northbound Ingest Service (NIS) as a read-only service that ingests telemetry and normalizes it into the Oversight TelemetryEvent contract.

The NIS will contain dedicated protocol adapters for:

  • Modbus TCP
  • OPC-UA
  • Ethernet/IP
  • MQTT / Sparkplug-B

Each adapter will establish controlled, read-only communication with approved field endpoints. The adapter does the following:

  • Terminates the source-protocol
  • Decodes the received data
  • Converts the data into an internal raw-observation representation

Protocol-specific identifiers (e.g., modbus register addresses, OPC-UA NodeIds, Ethernet/IP CIP object paths, and Sparkplug-B MQTT topics) will remain within the protocol adapters and telemetry mapping layers.

The internal raw-observation will then be passed to the NIS normalization layer. The normalization layer will use a telemetry mapping registry and will perform the following:

  • Determines the enterprise, site, area, line, asset, and tag identity
  • Converts the source value into the required data-type
  • Applies byte-order conversion where it is required
  • Applies configured scaling factors and offsets
  • Normalizes engineering units
  • Normalizes the source quality information into the Oversight quality model
  • Normalizes the source timestamp and assigns an ingestion timestamp
  • Detects malformed, stale, unsupported, or unmapped telemetry

The normalized telemetry will then be used to construct the TelemetryEvent. The NIS will validate the event with the supported schema before allowing it to be published to the UNS.

Using protocol buffers, the NIS will serialize the TelemetryEvent. It then contructs the NATS subject using the following format:

oversight.telemetry.<enterprise>.<site>.<area>.<line>.<asset>.<tag>

The NIS will then publish the Protobuf-serialized TelemetryEvent to the UNS subject. The NIS will confirm success only after receiving a JetStream PubAck.

Component Responsibilities

The NIS provides a controlled boundary between source protocol communication and the internal telemetry contract.

The Responsibilities of Northbound Ingest Service are as follows:

  • The NIS ingests telemetry through read-only connections to approved industrial telemetry sources.
  • It terminates source-protocol communication at the Northbound Ingest Service boundary. This is important because protocol-specific information must never be exposed to downstream consumers.
  • It reads and decodes the following industrial protocols:
  • Modbus TCP
  • OPC-UA
  • Ethernet/IP
  • MQTT / Sparkplug-B
  • It reads protocol-specific data, translates it into vendor-neutral Oversight ICS telemetry.
  • The NIS NEVER writes to the control assets, processes command subjects, detects anomalies, or performs any physical control.
  • The NIS normalizes data types, byte order, scaling, offsets, engineering units, quality, and timestamps.
  • It constructs and validates the Oversight TelemetryEvent.
  • It serializes the TelemetryEvent objects using Protocol Buffers.
  • It builds the semantic UNS subject from the TelemetryEvent.
  • It publishes the protobuf-serialized TelemetryEvent to the UNS subject oversight.telemetry.>.
  • It confirms the successful JetStream persistence through a published acknowledgement (PubAck).

MQTT / Sparkplug-B messages are decoded at the NIS boundary and mapped into the Oversight telemetry contract, rather than being forwarded directly to the UNS.

The NIS is Read-Only and does not replace PLC control logic, safety-instrumented systems, or deterministic control functions. It has no authority to write to field assets or execute control commands.
