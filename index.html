Cognitive Reliability & Predictive Failover Agent for Critical Infrastructure

Level 3.5 Industrial Middleware | AI-Driven Asset Orchestration

Project Status: In Development

Executive Summary

Oversight ICS is a scalable, real-time, event-driven distributed system that uses AI to orchestrate complex human-in-the-loop failover scenarios. It is implemented as a Safety-First, Human Governed AI-Driven Cognitive Reliability Layer for industrial control assets.

The Oversight system doesn’t replace the primary control hardware, it just supervises it. It maintains a Cognitive Digital Twin to monitor critical metrics by streaming asset telemetry through NATS JetStream and a streaming analytics service. By streaming asset telemetry through the message broker and stream processor, Oversight maintains continuous windowed $Z$-score drift analysis to detect logic deviations before they occur and trigger automated failovers before physical hardware fails.

Oversight implements strict decoupling from Safety Instrumented Systems (SIS) so that AI-driven intents and command proposals never compromise hard-coded safety interlocks. The Oversight system relies on a Command Query Responsibility Segregation architecture to separate the read and write paths of the system.

By using this architecture, Oversight can audit, trace, and reproduce, intents and commands at sub-second latency while still meeting the highest standards of industrial governance and safety.

Software Engineering & Tech Stack

Oversight ICS is built using an event-driven microservices architecture for edge deployments in industrial environments.

  1. Stream Processing: Custom Python streaming analytics service
  2. UNS & Messaging: NATS JetStream
  3. Orchestration: LangGraph, Ollama
  4. Database: TimescaleDB
  5. Vector Database: pgVector
  6. In-Memory Cache: Redis
  7. Backend/API: FastAPI (Python)
  8. Security & Hardware: RBAC, TPM 2.0 Hardware Signing, RS256-signed JWTs, Dual-NIC Edge IPC, Level 1.5 Arbitrator, Nginx Perimeter Gateway, Cgroup Resource Isolation, Cryptographic Notary Buffers
  9. Containerization: Docker Compose, GitHub Actions CI/CD, Linux Cgroups, Systemd Watchdogs
  10. Monitoring & Observability: Prometheus, Grafana, Loki (centralized log aggregation)
  11. Audit & Forensics: WORM-based Audit Storage, Immutable Historian, Distributed Tracing (trace.id), immutable commands, and event records

Installation & Local Development

Prerequisites

  • Operating System: Linux-based OS is required for compatibility with hardware interfaces and systemd watchdogs. Windows users must use a fully configured WSL2 environment.
  • Container Engine: Docker Engine 24.0+ & Docker Compose
  • NATS Server (w/ JetStream enabled): Required for the UNS & messaging layer.
  • Streaming Analytics Service: To consume the streaming data from the NATS JetStream for the UNS and perform windowed $Z$-score analysis.
  • Python 3.12+: Managed via uv
  • Node.js 20+: Required for local building and testing of the frontend dashboard.
  • C++ Build Tools: Requires full toolchain suite including build-essential, cmake, and a standard compiler to anchor the native C++ Southbound Driver.
  • (Optional) TPM 2.0 Emulator: For local hardware testing

Physical Hardware Requirements

The Edge Gateway is designed for deployment in industrial environments. Production hardware must meet the systems requirements below:

  • Form Factor: Industrial PC (IPC) with Fanless Passive Cooling to prevent ingress of dust/particulates.
  • Mounting: Heavy-duty integrated chassis tailored for standard 35mm DIN-Rail mounting inside field control cabinets.
  • Memory & Storage: Minimum 16GB Error-Correcting Code (ECC) RAM to prevent memory corruption during high-frequency telemetry tracking. Storage must be a minimum of 256GB industrial-grade SSD (SLC/pSLC enclaves) supporting unalterable log writes.
  • Hardware Secure Root (TPM 2.0): An active, provisioned physical TPM 2.0 module is strictly required.
  • Dual NIC Requirement: The IPC must have two independent physical 1GbE network interface cards (Intel i210/i211 preferred for native hardware-level PTP timestamping support):
  • Southbound OT NIC: Connected to the isolated process network (Levels 1–2) to interface with process assets.
  • Northbound IT NIC: Connected strictly to the Level 3.5 Industrial DMZ (IDMZ) infrastructure.
    • CRITICAL: IP Forwarding must be disabled at the host OS level to maintain a logical air-gap and prevent lateral traffic routing between zones.
  • Hardware Watchdog (PVP-02):An onboard physical watchdog timer (PVP-02) must be mapped to the system. The C++ Southbound Driver process must check this watchdog loop continuously; if the loop misses a heartbeat for >500ms, the physical DO-0 relay drops open, forcing the system to shed AI control and instantly fall back to local safety logic solvers.
  • Environmental & Enclosure: Operating Temperature: Ruggedized tolerance across a -20°C to 60°C without thermal throttling or clock jitter degradation.
  • Ingress Protection: Minimum IP40 if mounted inside a certified plant control cabinet; IP67 weatherproofing if deployed externally.
  • EMC Compliance: Enforced shielding on all active RJ45 ports paired with industrial surge protection arrays. Electrical resistance between the gateway chassis and plant common ground must check out at < 1 Ohm to mitigate electromagnetic interference generated by adjacent heavy machinery (VFDs, high-horsepower motors).
  • Power Framework: Integrated dual 24V DC terminal blocks supporting fully redundant power input lines backed up by an external industrial UPS deployment. [!NOTE] For local development and testing, you can use a standard PC or laptop. The hardware requirements are specific to production deployments in industrial environments.

Quick Start Guide

Development and Test Environment Setup:

  1. Clone the repository:

bash git clone [https://github.com/org/oversight-ics.git](https://github.com/ARMummert/oversight-ics.git) cd oversight-ics

  1. Environment Configuration: Copy the environment variables file (.env.example) and configure your .env file with the appropriate values.

    bash cp .env.example .env

  2. Install Python Dependencies

    Oversight Python dependencies are managed using uv.

    bash uv sync

    Verify the configured Python environment:

    bash uv run python --version

  3. Run the Test Suite

    Validate the software configuration before starting the local stack:

    bash uv run pytest

  4. Run Preflight Checks

    bash uv run python infrastructure/monitoring/compliance_watcher.py

    Note

    PTP, physical watchdogs, a TPM, and dual physical NICs are not required for normal local development unless those specific hardware-dependent behaviors are being tested.

  5. Start the Core Infrastructure

    Start the Docker Compose services:

    bash docker compose up -d

    Verify container status:

    bash docker compose ps

  6. Start the Northbound Ingest Service

    bash docker compose up -d northbound_ingest

    During local development, use simulated Modbus TCP, OPC UA, and EtherNet/IP endpoints rather than production control assets.

  7. Start the Stateful Streaming Analytics Service

    bash docker compose up -d streaming_analytics_service

  8. Build the Southbound Driver

Build the native C++ Southbound Driver:

bash cmake -S . -B build cmake --build build

!!! danger “Physical Writes”

   Building the Southbound Driver does not authorize connection to production control hardware.

  1. Start the Southbound Driver in Development/Test Mode

    Start the driver using the project’s development or simulator configuration.

    bash ./build/southbound_driver --config ./config/southbound_dev.yaml

  2. Start the Frontend Dashboard

    Install frontend dependencies and start the local development server:

    bash cd ui npm ci npm run dev

  3. Verify NATS JetStream

    bash nats server check jetstream

    Confirm that the NATS server is running with JetStream enabled and that the required Oversight streams, consumers, and subjects have been created.

    At minimum, verify coverage for the applicable namespaces:

    text oversight.telemetry.> oversight.commands.> oversight.events.> oversight.audit.> oversight.health.>

    Stream configuration must be validated before application services are allowed to depend on persistent messaging or command delivery.

  4. Verify NATS Streams:

    bash nats stream ls

  5. Verify System Health

    bash curl http://localhost:8000/health

  6. Verify Redis:

    bash docker compose exec redis redis-cli ping

  7. Verify TimescaleDB

    bash docker compose exec timescale pg_isready

  8. Verify the Northbound Ingest Service

    bash docker compose logs --tail=100 northbound-ingest

  9. Verify the Stateful Streaming Analytics Service

    bash docker compose logs --tail=100 streaming-analytics

  10. Check all Logs:

    bash docker compose logs --tail=100

  11. Run Ruff:

    bash uv run ruff check

  12. Shut Down the Development Environment

    bash docker compose down

    To preserve database and JetStream volumes, do not remove volumes unless the test procedure specifically requires a clean environment.

Production Deployment

The Quick Start Guide does not constitute a production commissioning procedure.

Production deployment requires separate validation of network segmentation, firewall rules, NATS subject permissions, TPM provisioning, RBAC, physical watchdog behavior, time synchronization, audit-storage immutability, fail-safe behavior, hardware redundancy, and FAT/SAT acceptance criteria before Oversight is granted write access to operational control assets.

Target Environment

Hardware: Industrial PCs (IPCs) with Dual-NIC network isolation Hardware-Rooted TPM 2.0 modules

Connectivity: Industrial environments using OPC-UA, Modbus TCP, EtherNet/IP, or MQTT-enabled process assets

Use Case: Critical Infrastructure (Wastewater, Energy, Manufacturing) where unplanned downtime exceeds the cost of redundant hardware.

Industrial Safety Protocol

SAFETY PROTOCOL: READ CAREFULLY

OverSight ICS is a Cognitive Reliability Agent, NOT a Safety Agent.

The system is strictly decoupled from the Safety Instrumented System (SIS). Hard-coded safety interlocks and physical E-Stops always maintain primary authority. OverSight operates as a Read-Verify-Suggest layer to prevent those safety limits from ever being reached.

Safety Decoupling is a critical design principle in OverSight ICS.

Caution

Logic Integrity Guardrail: The Southbound Driver is strictly prohibited from modifying PLC ladder logic or function blocks. It is limited to writing to a predefined Command Global Data block. In this instance, the AI Agent can only request state changes that have been pre-approved and hard-coded by the site’s control engineers.
