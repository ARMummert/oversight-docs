RFC-002 - Control Authority Model & Level 1.5 Arbitration

Author: Amy Mummert

Status: Proposed

Components: Level 1.5 Arbitrator, Semantic Gatekeeper, TPM 2.0 Hardware Signer, Two-Key Protocol, Global Manual Hold

Background / Context

This RFC outlines the control authority model and level 1.5 arbitrator service. The system must be able to support multiple levels of control authority. This layer is a zero-trust policy enforcement layer. It sits between the messaging layer (Level 3.5 IDMZ) and the deterministic control layer (Level 1). The arbitrator prevents unvalidated, out-of-bounds, or unauthorized write commands from reaching the physical plant assets.

Problem Statement

The physical plant floor requires strict determinism even though the agent and the stream processor operate asynchronously. If we were to let the agent or an unverified client write access directly to the physical plant floor, we could create a catastrophic failure. These include adversarial prompt injection, RAG poisoning, or runtime model hallucinations.

In addition, high-impact interventions require multi-person approval to prevent operator error under pressure. The system handles this by enforcing the Control Authority Model, which decouples the physical command execution from the AI reasoning execution.

Note

The core security problem here is not letting any software anomaly or model hallucination to ever bypass the MFA human authorization or the hardware cryptographic validation before touching the physical plant hardware.

Proposed Solution

The proposed solution is to implement a Level 1.5 Arbitrator service as a zero-trust policy enforcement layer that sits between the messaging layer (Level 3.5 IDMZ) and the deterministic control layer (Level 1). This architecture implements safe-state isolation buffers, dual-auth cryptographic validation, semantic range checking, and hardware-rooted TPM 2.0 signatures.

Control Authority Model

  1. The Level 1.5 Arbitrator receives a commmand from the NATS command queue (oversight.commands.proposed) it consumes the proposal and places it in an isolated stateful memory buffer. It then pauses execution and waits for validation.
  2. For high-impact changes, the arbitrator enforces the Two-Key Protocol. This protocol requires two distinct approvals (e.g., Operator and Plant Manager) before the command is executed.
    • The primary token validates the active field operator’s 8-hour shift RS256-signed JWT.
    • The secondary token validates the plant manager’s 8-hour shift RS256-signed JWT. This requires an independent X-Secondary-Authorization header containing a supervisor or safety lead claim.
    • The gateway will verify that primary_jwt.sub != secondary_jwt.sub to prove two-person integrity.

Semantic Gatekeeper

When the control authority model is authenticated, the payload is sent to the semantic gatekeeper. This component audits the intent against the following: - The Forbidden Register Lists - Physical Constraints such as P&ID operating limits and active interlock states.

Hardware Root of Trust (TPM 2.0)

If the semantic gatekeeper passes, the payload is handed to the Cryptographic Notary Buffers, which then invoke the local TPM 2.0 hardware to sign the payload with a root-of-trust signature. If a payload is modified or lacks this signature, it is immediately destroyed.

Tradeoffs and Alternatives Considered

I chose to use the Level 1.5 Arbitrator service because of its zero-trust nature.
